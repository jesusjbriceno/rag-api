# Tasks: adminapp-deployable-dashboard

Implementation tasks derived from `proposal.md` (Coolify revision) and `design.md` (Coolify revision) for change `adminapp-deployable-dashboard`. Strict TDD ordering: every executable task follows RED → GREEN → TRIANGULATE → REFACTOR. Single-threaded writes; one work unit at a time; tests committed with the behaviour they verify. No deploy, tag, push, manual publication, commit, or RDD activation is performed in any task — implementation-only verification (`dotnet test`, `docker build --target admin`, validator static checks, paired-view Compose validation, actionlint) is the bound.

The change completes the AdminApp BFF + image and integrates it into the existing `compose.coolify.yaml` stack as the sole publicly-reachable service. API, PostgreSQL, and llama.cpp remain internal to the default Docker network with no Compose-level publication mechanism (no `ports`, no host network, no public-routing metadata, no domains). Dokploy manifests, validators, and docs are not created or modified. Tailscale, SPA serving, and new API endpoints are out of scope.

Unit 1 (shared wire contract + validated host shell) is already implemented and is preserved with its full checkbox history and its `apply-progress.md` record. As of the Units 2–3 follow-up reconciliation, the Units 2 and 3 core runtime (authentication, assertion, machine proof, proxy, health endpoints) is implemented and unit-tested in a **consolidated layout** (`AdminAppHostWebApplicationExtensions.cs` and `tests/Rag.UnitTests/AdminAppTests.cs` rather than the per-file layout below). The endpoint-level integration tests and the Docker `admin` target now exist and pass; the remaining Unit 2 gaps are the per-operation `[Theory]`/unsupported-method integration rows and the planned `Auth/` extraction, kept honestly unchecked below. Units 4 and 5 remain pending; the new Unit 4 replaces the former Dokploy-oriented unit with the Coolify-boundary, paired-view validator, and operational runbook.
